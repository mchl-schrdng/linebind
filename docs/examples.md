# Reproducible examples

These are small **synthetic fixtures**, not production applications, upstream
incidents or evidence of adoption. They exercise the installed CLI, its Git
inputs, native checks, exit codes, JSON output and standalone HTML report.
By default, no Node.js, Python, database, Kubernetes cluster or project
dependencies are installed or executed. The optional data command example below
explicitly runs an installed Python interpreter.

| Context | Declared decision | Seeded violation | What this does not establish |
| --- | --- | --- | --- |
| [Frontend](../examples/frontend/base/.linebind.yml) | Runtime dependencies are limited to React and React DOM | Add jQuery to `dependencies` | Import resolution, bundle behavior or package safety |
| [Backend](../examples/backend/base/.linebind.yml) | `GET /orders` retains its documented `200` response | Replace that declaration with `201` | General OpenAPI compatibility or actual server behavior |
| [Data](../examples/data/base/.linebind.yml) | The table schema declares `order_id` as non-null | Change `nullable` to `true` | Uniqueness, nulls in actual rows or query correctness |
| [Infrastructure](../examples/infrastructure/base/.linebind.yml) | A Deployment requests `runAsNonRoot: true` at pod level | Change the field to `false` | Container overrides, image behavior or deployed cluster state |
| [Co-change](../examples/co-change/base/.linebind.yml) | Ship migration notes with SQL changes | Change SQL without editing the guide | Correctness of SQL, documentation or tests |

Each example contains a `base` tree and overlays, `crossed` and `unverified`.
The latter contains malformed JSON/YAML or an unavailable Git LFS pointer. Missing evidence must
be reported as incomplete verification, not as compliance or a proven violation.

For a first run with only Git and the installed binary, use the
[frontend walkthrough](try-it.md). The runner below is the broader contributor
validation suite. From the Linebind checkout, with Git and Go installed:

```sh
go build -o ./bin/linebind ./cmd/linebind
go run ./scripts/pilots -binary ./bin/linebind
```

On Windows, build `./bin/linebind.exe` and pass `-binary ./bin/linebind.exe` instead. To test
a release archive, extract it outside this checkout and pass that binary's path.
The runner accepts `-examples /path/to/linebind/examples` when run elsewhere.

The runner creates separate temporary Git repositories, commits each approved
contract, and checks these four states for every fixture:

1. **Passed:** unchanged declared input, exit `0`.
2. **Crossed:** the documented mutation, exit `1`, with a finding.
3. **Unverified:** malformed or unavailable input, exit `2`, with a diagnostic.
4. **Contract removed:** the violation plus deletion of `.linebind.yml`, exit
   `1`. The original rule must still find the violation, and the contract deletion
   must appear separately in the report.

The co-change fixture adds a fifth state: **repaired**, where SQL and its guide
both change and the check passes.

For every state, it also checks the resolved base SHA, approved contract digest,
JSON verdict, and HTML rendering. Rendering the saved JSON with `linebind report`
must reproduce the HTML generated by `linebind check`.

The evidence directory is printed and retained. It contains the reports, a
`results.json` index, and temporary repositories for inspection. Supply
`-out /path/to/new-directory` to choose its location. The destination must not
already exist. The runner never changes this checkout or an upstream repository.
CI runs the synthetic cases against extracted archives on its three OS runners.
The index records the binary version and SHA-256, host platform, runner Go
version, and generation time. Cross-compiling an archive alone does not establish
that it runs on its target platform.

## Data command: check actual transformation results

The [data-command contract](../examples/data-command/base/.linebind.yml) tests
actual rows returned by a candidate SQL transformation. This is an external
command example, not a native Linebind SQL check. It requires `python3` on `PATH`
with its standard-library `sqlite3` module; there are no pip dependencies or
database server to install.

```sh
go run ./scripts/pilots -binary ./bin/linebind -data-command
```

The approved
[checker](../examples/data-command/base/checks/check_orders.py) loads three rows
from a fixed [CSV fixture](../examples/data-command/base/checks/orders.csv) into
an in-memory SQLite database. It evaluates the candidate `transform.sql` and
requires a nonempty result with unique, non-null `order_id` values. The checker
and CSV are both `policy-files`: Linebind uses their approved base versions when
running a candidate. Changes to them require separate policy review.

Only SQL is taken from the candidate. The trusted checker permits reads of its
fixture table and a small set of SQLite functions; writes, attachments, other
tables and arbitrary Python are not supported. It bounds query work and result
size. These restrictions belong to this example checker; Linebind's host command
execution is not an OS sandbox.

The optional runner adds six cases:

| Candidate | Result | Meaning |
| --- | --- | --- |
| Original transformation | `passed`, exit `0` | All three output keys are unique and non-null |
| Replace every key with `101` | `crossed`, exit `1` | Duplicate keys in actual returned rows |
| Replace keys with `NULL` | `crossed`, exit `1` | Null keys in actual returned rows |
| Malformed SQL | `unverified`, exit `2` | The checker cannot evaluate the transformation |
| Attempt `DELETE` | `unverified`, exit `2` | Unsupported write rejected by the checker |
| Original transformation without execution opt-in | `unverified`, exit `2` | The command was not executed |

The runner supplies `--allow-exec` only for the five cases that deliberately run
this trusted checker. Its Python version is recorded in the evidence index.
Generic `format: exit` reports contain the declared command verdict and diagnostic
output; they do not invent structured findings or source locations. Passing
these three fixture rows does not establish correctness on production data, full
SQL compatibility, completeness of the transformation or general data quality.

The Linux external-tools CI job runs these cases with Python supplied by the
runner. The native checks remain usable without Python. Combine `-data-command`
and `-public` to run all 31 scenarios in one evidence directory.

## Public repository pilot: p-limit

This optional pilot uses the real
[sindresorhus/p-limit repository](https://github.com/sindresorhus/p-limit) at
[`a8a6fbec4e0e866d6d779b10889bb4f5567e70eb`](https://github.com/sindresorhus/p-limit/commit/a8a6fbec4e0e866d6d779b10889bb4f5567e70eb).
Its [package manifest](https://github.com/sindresorhus/p-limit/blob/a8a6fbec4e0e866d6d779b10889bb4f5567e70eb/package.json)
declares `"type": "module"`.

```sh
go run ./scripts/pilots -binary ./bin/linebind -public
```

`-public` explicitly enables a Git fetch of that exact commit into a new temporary
repository. The runner adds a
[Linebind-authored experimental contract](../examples/public-p-limit/.linebind.yml)
that preserves the observed ESM declaration. It commits that policy locally,
then tests the untouched manifest, a seeded `"type": "commonjs"` change,
malformed JSON, and the seeded violation with the policy removed.

The upstream commit and the local approved-policy commit are distinct and both
are recorded. No npm installation, project script or upstream test is run. No
issue, pull request, branch or tag is created upstream.

This is a **public snapshot with seeded mutations**. The policy is not supplied
or endorsed by p-limit's maintainer. Passing this pilot shows that the narrow
declared check runs on that snapshot; it is not a historical bug discovery,
architectural benchmark or adoption claim.

## Related changes (v0.5.0)

The [co-change fixture](../examples/co-change/README.md) requires migration notes
when SQL changes. Its five variants cover an unchanged repository, missing
companion edits, incomplete inputs, contract removal and a repaired delivery.
It runs in the same binary/JSON/HTML validation loop as the other native examples.
